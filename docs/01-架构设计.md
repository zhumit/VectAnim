# 架构设计

> [English](en/01-architecture.md) | 中文

## 1. 总体结构

```
┌────────────────────────────┐        ┌──────────────────────────────┐
│  Web 编辑器（TypeScript）    │        │  WPF 运行时（C#）             │
│                            │        │                              │
│  Fabric.js 画布             │        │  VectAnimViewer              │
│    ↕ 文档投影/回写          │        │    ↕                         │
│  EditorStore（唯一数据源）   │        │  VectAnimRuntime             │
│    ↕                       │        │    ↕                         │
│  Schema 校验/序列化          │        │  SceneRenderer               │
│    ↕                       │        │    ↕                         │
│  Runtime（预览）             │        │  DrawingContext              │
└─────────────┬──────────────┘        └──────────────┬───────────────┘
              │                                       │
              └────────── .vectanim.json ─────────────┘
                       （唯一数据契约）
```

三个模块、两条边界：

1. **编辑器**只产出描述，不做物理求解；
2. **Schema** 是唯一契约，两侧各自实现「解析 → 运行时模型 → 渲染」；
3. **运行时**只消费描述 + 变量，不反向修改文档。

## 2. 编辑器数据流

```
用户操作 → 工具/画布事件 → 命令（commands.ts）→ EditorStore.update()
                                                      │
                            ┌─────────────────────────┴──────────────────┐
                            ↓                                            ↓
                  CanvasView.render(doc)（投影到 Fabric）        面板重建（属性/变量/动画）
```

关键设计：

- **单一数据源**：`EditorStore` 持有不可变文档。Fabric 画布是它的「投影」，不是数据源。
- **拖拽不写文档**：拖动/缩放/旋转过程中只有 Fabric 内部变化，松手（`object:modified`）时一次性回写，避免每帧克隆文档。
- **回写时烘焙**：把 `scaleX/scaleY` 折算进几何，旋转保留为 `RenderTransform.Rotate`，因此文档里永远是「真实尺寸 + 一个角度」。
- **绑定锁定**：属性一旦绑定变量，对应交互被锁定（位置→禁移、尺寸→禁缩放、角度→禁旋转），防止用户操作与数据驱动互相覆盖。
- **历史合并**：同一属性的连续修改（700ms 内、同 coalesceKey）合并为一条撤销记录。

## 3. 两端共享的运行时语义

表达式、关键帧、外部优先级这三件事在 TS 与 C# 中**各实现一遍**，但逐条对齐（有对应的单元测试）。之所以不共享代码：跨语言共享要么引入代码生成，要么引入 WASM，都会把部署复杂度抬高；而这三块逻辑规模可控（约 600 行/端），对齐成本低于共享成本。

对齐清单：

| 语义 | TS 实现 | C# 实现 |
| --- | --- | --- |
| 词法/语法/优先级 | `engine/expression.ts` | `Expressions/ExpressionLexer.cs`、`ExpressionParser.cs` |
| 函数白名单与度制三角 | `EXPRESSION_FUNCTIONS` | `ExpressionFunctions.cs` |
| 关键帧采样与缓动 | `engine/keyframes.ts` | `Animation/KeyframeSampler.cs` |
| 变量优先级与依赖排序 | `engine/runtime.ts` | `Runtime/VectAnimRuntime.cs` |
| 颜色语义 | `engine/color.ts` | `Rendering/ColorParser.cs` |

两端都有对应的测试覆盖同样的用例（例如 `mod(-30,360)=330`、`EaseIn` 半程 < 0.5、`t=6` 且 `loopDelay=1` 时的采样值）。

## 4. 渲染管线（WPF）

```
LoadDocument
  ├─ DocumentValidator.Normalize   补默认值 / 剔除非法 / 排序关键帧
  ├─ VectAnimRuntime.LoadDocument  变量表 + 编译表达式 + 拓扑排序 + 首帧计算
  └─ SceneRenderer.Load            建立 ShapeRenderState（按 ZIndex 排序）

每帧（CompositionTarget.Rendering 或 SetVariable）
  ├─ runtime.Advance(dt)           推进 t，重算表达式/关键帧，返回「是否变化」
  ├─ scene.Update(store)           逐图形解析属性 → 脏检查 → 必要时重建几何
  └─ InvalidateVisual → OnRender
        └─ 背景 → 逐图形 PushTransform/PushOpacity → DrawGeometry → Pop
```

### 4.1 缓存策略

| 对象 | 缓存方式 | 失效条件 |
| --- | --- | --- |
| 几何 | `Geometry`（Freeze） | 几何相关属性的解析值变化（逐值比较签名） |
| 画刷 | `SolidColorBrush`（Freeze，按 ARGB 缓存） | 颜色变化 |
| 画笔 | `Pen`（Freeze，按颜色/线宽/线帽/拐角缓存） | 上述任一变化 |
| 变换 | `MatrixTransform` 复用实例，只改 `Matrix` | 变换值变化 |
| 视图矩阵 | 每帧按 `Stretch/Zoom/Offset` 计算（纯算术，无分配） | — |

`ShapeRenderState.Update` 的脏检查用**逐值比较**而不是哈希，避免哈希碰撞导致「偶发画错」这种最难排查的问题。

### 4.2 为什么不用 WPF Shape

- 每个 `Shape` 都是一棵带属性系统、布局、命中测试开销的可视化树节点；
- 200 个图形时，`Canvas + Shape` 的每帧开销主要在属性系统与布局，而不是绘制本身；
- `DrawingContext.DrawGeometry` 直接把绘制指令写入渲染树，几何/画笔已冻结，开销接近纯绘制。

实测（`VectAnim.RenderProbe`，200 个带旋转绑定的矩形，含 `RenderTargetBitmap` 导出开销）：**约 7.5 ms/帧**。

### 4.3 两种渲染模式

- `Drawing`：OnRender 直接画，默认；
- `Shapes`：把 `Path` 作为 Visual 子节点加入 `VisualCollection`，逐帧同步 `Data/Fill/Stroke/RenderTransform`。适合需要 WPF 原生特效/命中测试的场景。

两种模式共用同一套 `SceneRenderer` 状态，画面一致。

## 5. 坐标系与变换

### 5.1 统一坐标

- 世界坐标 = 画布坐标，左上角原点，Y 向下，单位 DIP；
- 所有图形的几何字段都在世界坐标（`Path` 除外：局部坐标 + `OffsetX/Y`）；
- 旋转中心 `CenterX/CenterY` 也是世界坐标。

### 5.2 变换顺序

```
p' = T(translate) · T(center) · R(angle) · S(scale) · T(-center) · p
```

WPF `Matrix` 的方法是「后置追加」（先调用的先生效），因此代码里必须按 **Scale → Rotate → Translate** 的顺序调用：

```csharp
var m = Matrix.Identity;
m.ScaleAt(sx, sy, cx, cy);
m.RotateAt(angle, cx, cy);
m.Translate(tx, ty);
```

这个顺序在 `CoreTests` 里有专门用例（`Scale, then rotate, then translate`），因为写反了只会表现为「图形位置偏一点」，肉眼极难发现。

### 5.3 与 Fabric 的差异处理

Fabric 用 `left/top + originX/Y=center + scaleX/scaleY + angle` 描述对象，导出时：

1. 取 `object.getCenterPoint()` 作为世界中心；
2. `scaleX/scaleY` 烘焙进几何（矩形宽高、椭圆半径、顶点按中心缩放、路径坐标缩放 + 重算 `Offset`）；
3. `angle` 写入 `RenderTransform.Rotate.Value`；
4. 直线直接把旋转烘焙进端点（避免旋转中心歧义）。

因此编辑器画布与 WPF 渲染的像素差异仅来自抗锯齿与线宽取整，不存在坐标偏移。

## 6. 错误处理策略

| 阶段 | 策略 |
| --- | --- |
| 导入 | 宽容：能修的修（补默认、去重、剔除非法），逐条记录 `Issue` |
| 导出 | 严格：有 error 级问题阻止导出并定位到字段路径 |
| 运行时加载 | 宽容 + 告警：坏图形跳过，坏表达式跳过，变量缺失按 0 |
| 渲染 | 单图形异常不影响整幅（几何构建 try/catch 后跳过该图形） |
| 交互 | 命中测试用几何而非包围盒，避免误命中 |

## 7. 目录结构

```
CavasEditor/
├─ editor/                      # Web 编辑器
│  ├─ index.html
│  └─ src/
│     ├─ schema/                # 数据契约：类型/校验/序列化/工厂
│     ├─ engine/                # 两端对齐的运行时语义 + Canvas2D 渲染器
│     ├─ editor/                # 编辑器逻辑：store/画布/命令/几何/SVG 导入/导出
│     ├─ ui/                    # 面板与主程序（无 UI 框架依赖）
│     ├─ styles/                # 深色工业风样式表
│     └─ tests/                 # Vitest 单元测试
├─ dotnet/
│  ├─ VectAnim.Wpf/             # 运行时类库（交付物）
│  ├─ VectAnim.Demo/            # WPF 演示程序（含 --smoke 截图模式）
│  ├─ VectAnim.Wpf.Tests/       # 控制台测试运行器（零依赖）
│  └─ VectAnim.RenderProbe/     # 离屏渲染探针（像素级断言 + 性能）
├─ samples/                     # 示例文档（编辑器与 Demo 共用同一份）
├─ tools/                       # 示例生成器 / 冒烟测试
├─ docs/                        # 文档
└─ artifacts/                   # 构建与验证产物（截图、渲染结果、nuget 包）
```

## 8. 技术选型理由

| 选择 | 理由 | 备选与放弃原因 |
| --- | --- | --- |
| Fabric.js v7 | 成熟的画布交互（拖拽/缩放/旋转/框选）开箱可用 | 自研画布交互工作量大且易出错 |
| Vite 8 + TS 5.9 | 构建快、类型安全、产物是纯静态资源 | Webpack 配置复杂；无构建则无法用 TS |
| 无 UI 框架 | 面板是表格/表单，手写 DOM 约 2k 行即可，避免框架体积与版本风险 | Element Plus 等会引入 100KB+ 且主题改造成本高 |
| 自研表达式引擎 | 白名单可控、无反射/无 `eval`、TS/C# 语义可逐条对齐 | NCalc 功能过宽（安全面大），且与 TS 端语义难对齐 |
| System.Text.Json | .NET 内置、零依赖、性能好 | Newtonsoft.Json 需额外包，功能重叠 |
| 扁平 Shape 结构 | 反序列化简单、容错好、跨语言一致 | 多态序列化（STJ 多态/自定义解析）复杂且易踩坑 |
